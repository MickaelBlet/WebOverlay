# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

WebOverlay: Tauri 2 desktop app (pure Rust, no npm, no UI) that opens websites listed in a TOML config as standalone "webapp" windows and injects user JS/CSS into every page. Targets Linux and Windows.

## Commands

```sh
cargo run -- --config examples/config.toml demo   # dev run (host needs WebKitGTK dev packages)
cargo run -- --config examples/config.toml --list
cargo test                                        # unit tests (config parsing, script generation)
cargo test wildcards                              # one test by name filter
cargo clippy --all-targets -- -D warnings
cargo fmt
scripts/check.sh                                  # fmt --check, clippy Linux + Windows (cargo-xwin), tests, all in Docker
scripts/build.sh                                  # release bundles in Docker -> dist-tauri/{linux,windows}/
scripts/build.sh --fast linux                     # one OS only, thin LTO (quicker rebuild)
scripts/build.sh --fast windows                   # quick Windows exe (portable exe, WebView2 loader linked statically)
```

- Only Docker + buildx are required on the host (any Linux, no WSL); host `cargo` commands need Rust and the WebKitGTK dev packages listed in README.md.
- `scripts/build.sh` = `docker buildx bake` (Dockerfile modeled on ../ProjectScaffold-Viewer): Linux deb/rpm/AppImage and Windows NSIS setup + portable exe via `cargo-xwin` (MSVC target), built in parallel (bake targets `linux` / `windows`, each exported to its own `dist-tauri/<os>`). Tool versions are pinned by digest/checksum in the Dockerfile (incl. `RUST_VERSION`, `TAURI_CLI_VERSION`, `CARGO_XWIN_VERSION`; tauri-cli and cargo-xwin are prebuilt release binaries). Crates are fetched once in the `deps` layer (keyed on Cargo.toml/Cargo.lock); `target` and `/root/.cache` (xwin CRT/SDK, tauri bundler tools) are per-OS cache mounts. `scripts/check.sh` = bake target `check` (stage `check`, `type=cacheonly` output, own `-check` caches). `--fast` (`FAST=1`) overrides the release profile via `CARGO_PROFILE_RELEASE_*` env and uses separate `-fast` target caches.
- Release builds use `windows_subsystem = "windows"` (`not(debug_assertions)` only): no console output on Windows (`--list`, `--help`, errors are invisible there). Debug builds / `cargo run` keep the console.

## Architecture

Flow: `main.rs` parses CLI and (unless launcher / `--edit`) loads config **before** Tauri starts (all errors surface early, nothing is opened on failure) → `inject::build_scripts` reads every script/style file into init-script strings → `window::open` builds one header + content window per app in `setup`.

- `config.rs`: serde structs with `deny_unknown_fields`; app `name` must match `[A-Za-z0-9_-]+` (it ends up in window labels, the profile dir and the AppUserModelID); `Config::load` = read + `Config::parse_at` (resolves script/style paths relative to the config file). Config lookup: `--config` > `config.toml` next to the executable (`$APPIMAGE` dir for AppImages) > `<config dir>/weboverlay/config.toml`. `allowed_hosts` defaults to the host of `url`; `*.x` also matches bare `x`. `wildcard_match` is the shared `*` matcher (case-insensitive).
- `inject.rs`: each style and each script becomes a **separate** `initialization_script` so a syntax error in one user file doesn't kill the others. Scripts are wrapped in an IIFE + `try/catch`, URL `matches` are compiled to anchored JS regexes, `run_at` maps to immediate / `DOMContentLoaded` / `load`. CSS goes through constructable stylesheets (`adoptedStyleSheets`, bypasses page CSP) with a `<style>` fallback. User content is embedded via `serde_json::to_string` (JSON string = valid JS literal).
- `window.rs`: each app = one undecorated `Window` (label `<name>`, Tauri `unstable` multiwebview) with two children: `<name>:header` (local `dist/header.html`, fixed `HEADER_HEIGHT`) above `<name>:content` (the remote site). Linux ignores child bounds (children are packed in the window's `GtkBox`), so `fix_header_height` makes the header a non-expanding GTK child; elsewhere `relayout` sets bounds on resize. Content: per-app profile via `data_directory` (`<local data dir>/weboverlay/profiles/<name>`, header shares it), `on_navigation` keeps allowed http(s) hosts and internal schemes in-app and sends the rest to the system browser (`tauri_plugin_opener::open_url`, called directly, plugin not registered); `on_new_window`: allowed hosts get a plain decorated `WebviewWindow` popup (`window_features` keeps `window.opener` for OAuth), others open externally. Content and popup builders share the `configure!` macro.
- `download.rs`: `on_download` (in `configure!`, so content and popups) lets the webview save into the downloads folder while an async `rfd` save dialog (built in the event, on the main thread) asks for the destination; `settle` moves the file there once both are done, or deletes it on cancel. The dialog opens on `Requested` (WebView2), else on `Finished`: WebKitGTK 2.52 never emits `decide-destination` to wry (destination chosen by WebKit), and Linux calls every webview's handler of the shared web context for one download (dedup on the saved path). `setup` (Linux only): a `decide-policy` handler downloads main-frame responses WebKitGTK cannot show (its default ignores them unless `Content-Disposition: attachment`), and a popup whose download started before any page loaded (`uri` empty) closes itself (the download goes on). Checked headlessly with Xvfb + `xdotool` driving the GTK dialog.
- `header.rs`: per-window state (`States`, keyed by window label: title, URL, zoom) pushed to the header with `header.eval("window.weboverlay.update(...)")` on content page load / title change / resize. `[app.header]` (color, `hide`) reaches the header once as an initialization script (`setup_script` → `window.weboverlaySetup`: CSS vars + hidden `data-item`s), applied before first paint. `header_action` is the only command; the header calls it via `window.__TAURI_INTERNALS__.invoke` (no npm, no `withGlobalTauri`) and it rejects callers other than `<window>:header`. Window controls are done in Rust, so no `core:window:*` permissions are needed. Favicon: `refresh_favicon` runs `FAVICON_JS` in the content with `eval_with_callback` (on load and title change; no page IPC) and `sanitize_favicon` keeps only http(s) / `data:image/` URLs before they reach the privileged header.
- `icon.rs`: when the favicon changes, a thread downloads it with `ureq` (page/header can't read cross-origin image bytes), falls back to `/favicon.ico` then the app icon, and `window.set_icon`s it (Linux X11 only; Wayland uses the `.desktop` file). Tauri's `set_icon` only sets Win32 `ICON_SMALL`, so on Windows `set_taskbar_icon` also sends `WM_SETICON ICON_BIG` (taskbar / Alt+Tab), resized to `SM_CXICON`, destroying the HICONs it created. The `image` dependency enables more formats in `tauri::image::Image::from_bytes`; SVG favicons (incl. `data:image/svg+xml,` emoji `<text>` icons) are rasterized with `resvg` using system fonts (loaded once), with file `<image href>` disabled. The Docker image has `fonts-noto-color-emoji`, so `scripts/check.sh` exercises emoji rendering (`WEBOVERLAY_ICON_OUT=<png path>` saves the test render when run on a host). `set_app_id` gives each app window (and its popups) its own AppUserModelID `dev.blet.weboverlay.<FNV-1a hash of the lowercased absolute config path>.<name>` (`AppWindow::config_path`) → separate taskbar buttons on Windows, plus the relaunch properties (`RelaunchCommand` = `"<exe>" --config "<config>" <name>`, `RelaunchDisplayNameResource`, `RelaunchIconResource`) so a pin relaunches the right app; the favicon is saved as `<local data dir>/weboverlay/icons/<aumid>.<content hash>.ico` (`write_pin_icon`; `pin_icon_path` = newest one; property set on the main thread) because the pin icon must be a file, named by content since the shell caches icons by path. Windows copies these properties into a shortcut when pinning (`User Pinned\TaskBar`, kept after an unpin in `User Pinned\ImplicitAppShortcuts\*`), and for windows with that AUMID the taskbar then shows the shortcut icon, ignoring `WM_SETICON`: `sync_shortcuts` (from `set_app_id` and `save_pin_icon`) rewrites the icon of shortcuts carrying the app AUMID and sends `SHChangeNotify(SHCNE_UPDATEITEM)` (without it the taskbar keeps the old one). The app `icon` key replaces the favicon: `load_configured` decodes it in `prepare` (and the launcher pre-check) into `AppWindow::icon`, `apply_configured` sets it on the window (also writes the launcher cache and the pin `.ico` before `set_app_id`), popups get it too, `update` then ignores favicon changes; launcher cards decode it directly (`file_data_url`), and the header gets it as a `data:` URL (`WindowState::icon`, sent instead of the page favicon by `push_state`).
- `editor.rs` + `dist/editor.html`: decorated `WebviewWindow` `weboverlay:editor` (the `:` can't clash with an app label), opened by `--edit` (no `Config::load`, so a broken/missing config is editable) or the header `edit` action (`open_later`: built from a worker thread, since a window built inside a sync command stays blank on Windows and `run_on_main_thread` runs inline on the main thread). Commands `editor_files/read/write/restart` reject callers other than the editor webview, and read/write only paths listed by `files()` (config + scripts/styles of the **saved** config). Writing the config runs `Config::parse` first and refuses invalid TOML; CRLF files keep CRLF. Restart checks `Config::load`, spawns `config::exe_path()` with the original args minus `--edit` (`strip_edit_flag`), then exits. Page JS = ES modules in `dist/editor/` (`main.js` files/buffers/wiring, `core.js` state + helpers, `highlight.js` sticky-regex tokenizer drawn in a `<pre>` under a transparent `<textarea>`, `view.js` monospace geometry (offset ↔ line/col/pixels, tab-size 2) + decoration boxes in `#deco` (current line, brackets), `edit.js` editing commands, `keymap.js` shortcuts: VSCode names matched on `e.key`, then on the physical US key for punctuation, `complete.js` suggest widget + hover card + JS/CSS completion (DOM members by reflection on the editor's own `window`, CSS properties from `CSSStyleDeclaration`, values filtered with `CSS.supports`), `toml.js` config context parser (table / key / value at the caret) + TOML completion and hover from the schema, `check.js` live validation, `find.js` find/replace widget (matches drawn in `#deco`), `palette.js` quick open / `>` commands (the labelled `keymap.js` commands) / `:` go to line). Modules talk through `core.js` `on`/`emit` (`change`, `caret`, `open`, `keydown`, `openFile`); widgets handle `keydown` before the shortcuts. `src/schema.rs` documents every config key (served by `editor_schema`; its tests parse every key and value, so a renamed key fails them); `editor_check` runs `Config::parse` on the unsaved text and returns the TOML error span in UTF-16 offsets. Every edit goes through `edit.replaceRange` (`execCommand("insertText")` keeps the native undo stack).
- `launcher.rs` + `dist/launcher.html`: undecorated `WebviewWindow` `weboverlay:launcher` (the page's 30 px `#bar` is the title bar; `launcher_window` = minimize / maximize / close / drag, returns the maximized state), opened when there is no app and no `--config` (`Mode::Launcher`, no `Config::load`). Lists recent apps (`<local data dir>/weboverlay/recent.json`, written by `launcher::record` from `prepare` on every normal launch, dedup on config + app, max 10, paths via `std::path::absolute`) and the apps of `config::portable_path()` (only when present), `config::user_path()` and the `added` configs (`<local data dir>/weboverlay/configs.json`). `launcher_create` (async) shows an `rfd` save dialog built on the main thread like tauri-plugin-dialog does (that plugin is not used: its init script overrides `alert`/`confirm` in every page), writes `NEW_CONFIG` unless the file exists, adds it to `configs.json` and opens the editor; `launcher_forget` only removes it from the list, `launcher_forget_recent` removes an entry of `recent.json`. The page merges recent + config apps into one grid (key = config + app, `collect` = recent order first), shown sorted by the `#sort` select (title A→Z default, Z→A, or the `collect` order; kept in `localStorage`), configs live in a header popover; search, sort, arrow-key nav and the per-app menu are plain page JS. `launcher_open/edit` reject callers other than the launcher and only accept configs/apps currently listed, pre-check `Config::load` + `build_scripts` (the child would fail silently), then spawn `exe --config <path> [<app>]` / `--edit --config <path>` (child reaped from a thread); the launcher stays open and refreshes on focus. Card icons: `icon::update` caches every applied favicon as `icons/<aumid>.png` (64 px max, all OSes); `launcher_list` returns them as `data:` URLs, and the page calls `launcher_icon` (async, listed apps only, once per run) for the others, which fetches `<url origin>/favicon.ico` into the same cache.
- No white flash: windows are built `.visible(false)` and shown on the first `PageLoadEvent::Finished` of their local page (app window: the header; launcher/editor: `window::show_when_loaded`); the content webview is hidden until its own `Finished`, the window background showing meanwhile. Window and local webview backgrounds follow `window.theme()` (`theme_color` with `HEADER_BG` / `PAGE_BG`, keep in sync with the pages' `--bg`). The content webview keeps its default (white) background: sites without a CSS background rely on it.
- Navigation shortcuts in the content are a plain init script (`inject::SHORTCUTS_SCRIPT`), no IPC.
- Security model: no capabilities file and no `remote.urls`. Tauri allows app commands only to local origins when no app ACL manifest exists, so the remote content gets `"... not allowed"` for `header_action` (verified on Linux and Windows). Adding a capability or `AppManifest` changes this: re-check that remote content stays denied.
- `dist/index.html` is only a placeholder required by `generate_context!`; `dist/header.html` is the header UI (self-contained, light/dark). `tauri.conf.json` declares no windows (all created in code). `gen/` is generated by `tauri-build` (gitignored): don't edit. App icons live in `icons/` (`build.rs` emits `rerun-if-changed=icons`: `tauri-build` only watches `tauri.conf.json`, so a changed icon would otherwise keep the stale embedded one in cached builds).

## Notes

- Injection is main-frame only (`initialization_script`, not `_for_all_frames`). Scripts run in page context and remain subject to page CSP for `eval` etc.
- Script/style files are read once at startup; changes need an app restart.
- X11 check of the window icon: run with `GDK_BACKEND=x11`, then `xprop -name <page title> _NET_WM_ICON | head -c 60` shows the icon size.
- Back/forward buttons are always enabled (no can-go-back API). SPA URL changes only reach the header on title change.
- Live behaviour can be checked headlessly-ish: serve a local page (`python3 -m http.server`), point an app at it, and have test scripts beacon results back via `new Image().src = "/beacon?..."` read from the server log (e.g. content `innerHeight` = window height − 30 checks the header layout). Header actions can be exercised by temporarily adding `invoke(...)` calls to `dist/header.html`.

## Conventions

- Update `CHANGELOG.md` `[Unreleased]` (Keep a Changelog) and `README.md` for user-visible changes; update `examples/config.toml`, the config section of `README.md`, `launcher::NEW_CONFIG` and `src/schema.rs` (editor docs/completion) when the config format changes. A release removes the `[Unreleased]` heading: add it back above the latest version (its compare link at the bottom stays).
- Before committing: `cargo fmt`, then `scripts/check.sh` (fmt check, clippy Linux + Windows, tests).
- Commit each finished feature or fix with the `commit-gpg` skill (GPG-signed commit, CHANGELOG checked).
